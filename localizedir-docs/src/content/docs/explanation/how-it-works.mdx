This page explains what happens between the attribute you write and the code the compiler sees. Understanding the pipeline helps you predict compile errors, reason about binary size, and use the generated API without surprises.

## The pipeline

When the compiler hits `#[localizedir("locales", ...)]`, the macro runs four stages before it emits any code:

<Steps>

1. **Parse.** A `syn` parser reads the attribute: one positional string literal for the base path plus the optional `fallback`, `parent`, and `case` options. Unknown keys, duplicate keys, and non-literal values fail here, at the exact token.
2. **Validate the input.** The decorated item must be a non-generic enum with at least one unit variant. Fielded variants, generics, and empty enums are rejected before the filesystem is touched.
3. **Resolve names.** The parent folder comes from `parent = "..."` or is inferred from the enum name (suffix strip + snake_case); each variant becomes a directory name through the `case` scheme or its `#[dir_name]` override. Duplicate directory names fail here.
4. **Anchor and validate the path.** `$VAR`s are expanded the way `include_dir!` expands them, relative paths anchor at `$CARGO_MANIFEST_DIR`, and the macro scans the base directory: locale names are collected (sorted, de-duplicated), and every `(locale, variant)` directory must exist. Anything missing fails the compile with the full list.

</Steps>

Only after all four stages succeed does code generation start — so a generated enum always describes a tree that exists.

## The generated code

The expansion contains three pieces:

<Code lang="rust" code={`// 1. Your enum, re-emitted without the #[dir_name] helper attributes.
//    Doc comments and other attributes are preserved.

// 2. A hidden inherent block: the single embed plus a path helper.
#[doc(hidden)]
impl AuthDirs {
    const LOCALIZEDIR_BASE: ::include_dir::Dir<'static> =
                    ::include_dir::include_dir!("$CARGO_MANIFEST_DIR/tests/fixtures/localized");

    fn localizedir_path(&self, locale: &str) -> ::std::path::PathBuf {
                    ::std::path::Path::new(locale)
                                    .join(Self::parent_folder())
                                    .join(self.dir_name())
    }
}

// 3. The LocalizeDir impl: metadata from literals, lookups via get_dir.
impl ::localizedir::LocalizeDir for AuthDirs {
    fn available_locales() -> &'static [&'static str] {
                    &["de", "en", "fr"] // discovered at compile time, sorted
    }
    fn try_to_localized_dir(&self, locale: &str) -> Option<&'static ::include_dir::Dir<'static>> {
                    Self::LOCALIZEDIR_BASE.get_dir(self.localizedir_path(locale))
    }
    // … base_path, parent_folder, dir_name, full_path, and the
    //   fallback override only when fallback = "..." is configured.
}`} />

Because the generated code is plain, documented Rust, rust-analyzer navigates it like hand-written code — go-to-definition lands on real methods, not macro internals.

## Why one embed matters

An obvious alternative implementation embeds each `(variant, locale)` directory separately. That approach expands `include_dir!` once per pair: with 12 variants and 6 locales, the same tree is re-walked, re-serialized, and re-typechecked 72 times. `localizedir` embeds the whole base directory **exactly once** and treats every lookup as a path comparison inside that one static tree.

The consequences:

- **Compile time stays flat** as the template tree grows, and does not scale with `variants × locales`.
- **Runtime fallback is free** — with a `fallback` configured, a missing locale is resolved by a second `get_dir` on the same tree, not by generated code paths.
- **Binary size is paid once** for the tree, no matter how many enums reference it. Two enums pointing at the same base path each hold a constant pointing into the same embedded data.

## Why locale discovery is compile-time

Scanning the base directory at compile time buys two properties that runtime scanning cannot offer:

1. **Structural typos fail the build.** A deleted or renamed variant directory is a compile error listing the exact missing paths — not a 404-shaped runtime surprise in production.
2. **Metadata is free forever.** `available_locales()`, `has_locale()`, and the lookups read generated literals and a static tree; there is no filesystem access, no locking, and no allocation on the lookup hot path beyond one `PathBuf` join.

The trade-off is intentional: the set of locales is fixed at build time. Adding a locale means adding a directory and recompiling — the same contract `include_dir` itself makes about files.

## Why lookups are exact-match

The lookup key is the directory name, compared exactly. There is no case-folding (`"FR"` does not match `"fr"`), no separator normalization (`"en-US"` does not match `"en"`), and no BCP-47 prefix matching. Normalization would cost an allocation per lookup and would silently guess what you meant, hiding typos. The [unknown-locales guide](/guides/handle-unknown-locales/) shows the negotiation layer to add in front when you need it.
